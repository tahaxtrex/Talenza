🖥️ 1. Development Environment

Google Antigravity (Primary IDE — all 3 team members)

What it is: Google's agent-first IDE, released November 18, 2025 alongside
Gemini 3. Built on a fork of Windsurf (which was acquired for $2.4B),
powered primarily by Gemini 3.1 Pro with full support for Claude Sonnet 4.6.

Why we chose it over Cursor:

  • Manager Surface — a dedicated interface to spawn, orchestrate, and observe
    multiple agents working asynchronously across different workspaces simultaneously.
    One team member can have a "Backend Agent" refactoring the pipeline while they
    work on the frontend in the Editor View — without context switching.
  • Artifacts system — agents generate verifiable deliverables (task lists,
    implementation plans, diffs, browser recordings) rather than raw tool calls.
    You review and approve before anything merges.
  • Knowledge Items — persistent project memory. Define once: "This project
    uses n8n webhooks, Claude Sonnet 4.6, and static JSON data." Every future
    agent request respects that context automatically.
  • AgentKit 2.0 (released March 15, 2026) — 16 specialized agents, 40+
    domain-specific skills, full-stack capabilities from ideation to deployment
    in one platform.
  • Free in public preview with generous rate limits on Gemini 3 Pro.

Honest limitation:

Context window grows rapidly during long sessions — known to cause lag.
Fix: restart the agent window frequently during the hackathon.
Native integrations are skewed toward Google Cloud; AWS deployment
requires terminal commands rather than one-click deploy. That is fine
for our use case — we use the terminal anyway.

Model support inside Antigravity:

  • Gemini 3.1 Pro (default, generous rate limits)
  • Claude Sonnet 4.6 ✅ (explicitly supported)
  • Claude Opus 4.6 ✅ (explicitly supported)
  • GPT-OSS-120B (open-source OpenAI variant)

Download: antigravity.google/download

Docs: developers.googleblog.com/build-with-google-antigravity

🧠 2. LLM Selection — Verified as of March 27, 2026

Why NOT one single model for everything

Different agents have different jobs. Matching model capability to task
complexity is real engineering. It also signals to the judges that you
evaluated options, not just defaulted to one API.

Agent 1 — Context Agent → Claude Sonnet 4.6

Task: Receive role + scenario → produce weighted competency matrix as JSON

Why Sonnet 4.6:

This agent requires structured output reliability and nuanced reasoning
about business context. Sonnet 4.6 leads the GDPval-AA Elo benchmark
at 1,633 points — the highest of any model tested — which specifically
measures expert-level office and knowledge work. This is exactly that task.

Why NOT Gemini 3.1 Pro here:

Gemini 3.1 Pro is still in preview as of March 27, 2026. Production SLAs
are not guaranteed. During a live demo, a 100-second response time from
a preview model is a demo-killing risk. The data is clear: Claude Sonnet 4.6
is GA, stable, and leads on expert task quality.

API config:

model: "claude-sonnet-4-6",
max_tokens: 1000,
temperature: 0.2  // Low = consistent structured outputs

Agent 2 — Profile Scoring Agent (×6 parallel) → Claude Haiku 4.5

Task: Score one candidate against the competency weights → return
per-dimension scores with one-line reasoning

Why Haiku 4.5:

6 parallel API calls. Speed matters — the judge is watching a loading screen.
Haiku is significantly faster and cheaper than Sonnet. The task is
well-structured enough that heavy reasoning is not required.

Critical caveat: Test this before committing. If Haiku's reasoning
reads as thin or generic (e.g., "Score: 7/10 — good experience"),
upgrade to Sonnet 4.6. Shallow agent outputs will cost you points
in the AI & Agent Quality category (20 pts). The cost difference
is small at hackathon scale. Don't be cheap here if quality suffers.

API config:

model: "claude-haiku-4-5-20251001",
max_tokens: 600,
temperature: 0  // Zero = deterministic scores across demo runs

Agent 3 — Decision Agent (Internal vs. External) → Claude Sonnet 4.6

Task: Weigh all scored candidates + scenario → recommend sourcing strategy
with 4-cost breakdown (Opportunity Cost, Execution Risk, Cultural Damage, Time Cost)

Why Sonnet 4.6:

Most consequential output in the system. Must produce nuanced,
defensible recommendations. Sonnet 4.6 at 0 temperature =
reproducible reasoning judges can interrogate.

API config:

model: "claude-sonnet-4-6",
max_tokens: 1500,
temperature: 0

Agent 4 — Scenario Comparison Agent → Claude Sonnet 4.6

Task: Re-rank all candidates under each of the 4 scenarios →
produce delta table showing rank changes

Why Sonnet 4.6:

This is your demo centerpiece. The animated re-ranking when scenario
switches must be logically consistent and explainable. No room for
inconsistent outputs. Sonnet 4.6's adaptive thinking handles
multi-step comparison reliably.

API config:

model: "claude-sonnet-4-6",
max_tokens: 2000,
temperature: 0  // Absolutely deterministic — same input, same ranking

What about Gemini 3.1 Pro?

Benchmark reality as of today:

  • Leads on 13 of 16 major benchmarks including ARC-AGI-2 (77.1%) and
    abstract reasoning
  • 7x cheaper than Claude Opus 4.6
  • 1M token context window (stable, not beta)
  • Leads on autonomous agent tasks in benchmark settings

Why we're not using it in the live demo pipeline:

Still in preview. Not GA. Response times exceeded 100 seconds under
load at launch. Not guaranteed stable for a live demo. For a project
where the demo IS the submission, this is an unacceptable risk.

Where Gemini 3.1 Pro DOES belong in this project:

Use it inside Google Antigravity for code generation and scaffolding
during development. You get the model's full capability during build
time, with zero risk during demo time. Best of both worlds.

🔄 3. Agent Orchestration

n8n — Self-Hosted on AWS ECS Fargate

What it is: Open-source workflow automation platform. Visual, node-based
pipeline builder. 400+ integrations. Custom JavaScript support.
Production-grade error handling, retries, and execution logs.

Why n8n over Google Opal:

This is not a close comparison.

Dimensionn8nGoogle Opal
Multi-agent orchestration✅ Full support❌ Bottleneck beyond linear flows
Custom API chaining✅ Native❌ Not supported
Webhook handling✅ Production-grade❌ Limited
Error handling + retries✅ Built-in❌ No testing framework
Self-hosting / data control✅ Full❌ Locked in Google ecosystem
Visual pipeline (for demo)✅ Shows in video✅ Also visual
Production SLA✅ GA, stable❌ Google Labs experiment
Longevity riskLowHigh (many Google Labs products die)

Opal is a rapid-prototyping toy for non-technical users inside Google Workspace.
It cannot do what n8n does. The correct mental model: Opal for ideas,
n8n for execution. We need execution.

Why self-host on AWS instead of n8n Cloud:

Two reasons. First, n8n Cloud's free tier has execution limits that
could fail during a demo. Second — and more importantly — AWS deployment
is the entire point. It demonstrates production-level SWE skills.
n8n Cloud hides the infrastructure. AWS ECS makes it visible and impressive.

The n8n pipeline structure:

WEBHOOK TRIGGER (receives: roleTitle, scenarioId)
    │
    ▼
NODE 1 — HTTP Request → Claude API (Context Agent)
    Input:  roleTitle + scenarioId
    Output: { weights: { crisis_mgmt: 0.35, ops_depth: 0.30, ... } }
    │
    ▼
NODE 2 — Split In Batches → 6 parallel HTTP Requests → Claude API (Profile Agent)
    Input:  Each candidate profile + weights from Node 1
    Output: { candidate_id, scores: [...], reasoning: [...] }
    │
    ▼
NODE 3 — Merge → HTTP Request → Claude API (Decision Agent)
    Input:  All 6 scored candidates + scenarioId
    Output: { recommendation, sourcing_strategy, four_cost_assessment }
    │
    ▼
NODE 4 — HTTP Request → Claude API (Scenario Comparison Agent)
    Input:  All 6 candidates (unscored) + all 4 scenario weight sets
    Output: { rankings_by_scenario, delta_table }
    │
    ▼
RESPOND TO WEBHOOK → Returns full JSON to Lovable frontend

The n8n canvas showing this pipeline = your architecture diagram.
Show it for 10 seconds in your video at the 2:20 mark.

Export the workflow: In n8n, export as workflow.json and commit
to GitHub. Judges can import and inspect the full pipeline.

☁️ 4. AWS Infrastructure

Why AWS over Vercel

Vercel is a frontend deployment platform. It is genuinely excellent
for what it does — but it hides all infrastructure decisions from you.
A judge who is from BMW's Digital Excellence Hub will look at a
Vercel deployment and see "they used a platform." They will look at
an AWS ECS deployment and see "they can manage cloud infrastructure."

You asked to show SWE skills. AWS is that proof.

AWS ECS Fargate — for n8n container

What it is: Fully managed serverless container service.
You define a Docker container (n8n's official image), ECS runs it.
No EC2 instances to manage. No Kubernetes cluster to configure.

Why ECS Fargate and NOT EKS:

EKS (Kubernetes) is the correct choice for large-scale, multi-service,
production microservices architectures. For a hackathon, EKS setup
alone takes 4-6 hours minimum. EKS requires: cluster creation,
node groups, kubectl configuration, IAM roles, namespace setup,
persistent volumes, and ingress controllers.

ECS Fargate gives you: container running in 20 minutes,
Application Load Balancer in another 10. It is genuinely
production-grade — major companies run critical workloads on ECS Fargate.
It is not a toy. The n8n documentation itself recommends ECS for
production deployments at moderate scale.

The correct framing for judges: "We chose ECS Fargate over EKS
because our workload is a single stateful service that doesn't require
Kubernetes' multi-cluster orchestration capabilities. ECS Fargate
provides the right abstraction for this scale while demonstrating
production AWS infrastructure patterns."

That answer signals senior engineering judgment, not simplicity.

Architecture on AWS:

Internet
    │
    ▼
AWS Application Load Balancer (ALB)
    HTTPS termination via ACM certificate
    │
    ▼
AWS ECS Fargate Cluster
    Task Definition: n8n container (n8nio/n8n:latest)
    CPU: 1 vCPU | Memory: 2 GB
    Auto-scaling: Min 1, Max 2 tasks
    │
    ▼
AWS EFS (Elastic File System)
    Persistent storage for n8n workflow data
    Survives container restarts
    │
AWS Secrets Manager
    ANTHROPIC_API_KEY
    N8N_ENCRYPTION_KEY
    (Never in code, never in environment variables in plaintext)
    │
AWS CloudWatch
    Container logs
    Execution metrics
    Alert if pipeline fails during demo

Services used:

AWS ServicePurposeEst. Cost (72hr hackathon)

IaC with AWS CDK:

Define all resources in code using AWS CDK (TypeScript).
This is what impresses judges — not clicking through the AWS console,
but having infrastructure-as-code committed to GitHub.

/infrastructure
  └── lib/
      ├── n8n-stack.ts      ← ECS cluster, Fargate service, ALB
      ├── storage-stack.ts  ← EFS mount

# Deploy entire infrastructure in one command:
cdk deploy --all

🎨 5. Frontend

Lovable (Primary UI Platform)

Hackathon code: HACKATHON2026

What it gives you: React + shadcn/ui + Tailwind, GitHub integration,
public URL, auto-deploy on push.

Lovable → GitHub → AWS flow:

Lovable generates React code
    → Auto-commits to GitHub repo
    → Lovable hosts frontend at public URL (for submission)
    → n8n webhook URL points to AWS ALB endpoint

The frontend calls the n8n webhook. n8n runs on AWS.
The two layers are decoupled and independently verifiable.

Prompting strategy for Lovable — always use this 3-part structure:

PART 1 — COMPONENT: What to build, with specific layout description
PART 2 — DATA: Exact JSON shape the component will receive
PART 3 — BEHAVIOR: What happens on every user interaction

Never say "build a hiring tool." Always say:

"Build a scenario selector component. 4 cards in a 2×2 grid.
Each card has: a lucide-react icon, bold title, 2-line description,
left border color (red=#DC2626 for Crisis, blue=#0066CC for Transformation,
green=#16A34A for Growth, gray=#374151 for Succession). Selected card
gets a bright border + checkmark overlay. One selection at a time.
Fires onSelect(scenarioId: string) on click. Dark background #0F172A."

Key Lovable features to use:

  • Shadcn/ui components — use Card, Badge, Progress, Tabs natively
  • Recharts — for animated competency score bars and ranking delta charts
  • Skeleton loading states — while agents process (judges see the pipeline working)

AWS Secrets Manager (API Key Security)

Non-negotiable. Never put API keys in code or .env files committed to GitHub.

// In your agent code — retrieve at runtime
const secret = await secretsManager.getSecretValue({
  SecretId: 'contexthire/anthropic-api-key'
});

If a judge opens your GitHub and sees sk-ant-... anywhere,
you are disqualified and your API account is compromised.
This is not a hackathon concern — it is a security concern.

AWS CloudWatch

Role: Log every agent execution during the demo.

Why this matters: if something goes wrong during the live demo,
you can point to CloudWatch and say "here are the execution logs —
you can see each agent fired sequentially." That turns a demo failure
into a debugging demonstration. Still impressive.

Set up a CloudWatch dashboard showing:

  • n8n container health
  • Number of pipeline executions
  • Average response time per agent

Show this dashboard briefly in your video. It signals production thinking.

Postman (API Testing During Development)

Role: Test each agent endpoint individually before wiring to frontend.

Create a collection: "ContextHire Agents"

POST /agent/context     → test with role + scenarioId
POST /agent/profile     → test with one candidate + weights
POST /agent/decision    → test with all scored candidates
POST /agent/scenario    → test full comparison output

When each agent passes in isolation, wire the pipeline.
Never debug agents and frontend simultaneously — too many variables.

ChatGPT-5 (Synthetic Data Generation Only)

Role: Generate the 6 synthetic candidate profiles.
This is the single best use of ChatGPT in this project.

Why ChatGPT for this specific task: GPT-5 produces the most
convincingly human-sounding professional biographies with
specific quantitative details, BMW-relevant terminology,
and realistic internal tensions between strengths and weaknesses.

Prompt template:

"Generate a realistic synthetic executive profile for BMW.
Include: full name (German/European), current role and employer,
14 years experience, 3 specific career achievements with
real-sounding metrics (€ amounts, headcount, percentages),
a 360-degree feedback quote that reveals both a strength and
a developmental tension, and a one-paragraph leadership narrative.
Make the profile conflicted — strong in operations, weak in
digital transformation. Do not use generic language."

Do this for all 6 profiles. Each profile should take 5 minutes.
Total: 30 minutes. This is the most impactful 30 minutes
in your entire 72 hours.
